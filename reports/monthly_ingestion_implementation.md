## 1. Files Changed
- **`app/main.py`**: Added new isolated logic for `/history/upload-preview` and `/history/upload-confirm`. Added directory creation logic for `HISTORY_STAGING_DIR`.
- **`frontend/index.html`**: Added a completely new distinct "Historical Snapshots Upload" card inside the Data Management View, separated from operational updates.
- **`frontend/app.js`**: Replicated the upload lifecycle patterns for `btn-history-upload-preview` and `btn-history-upload-confirm`, handling client-side display of detailed row-level array errors.
- **`scripts/test_history_ingestion.py`**: Created an exhaustive test suite directly importing FastAPI handlers and injecting MockUploadFile objects.

*(Note: `app/historical_store.py` did not require modifications because its idempotency and return patterns correctly mapped to requirements once upstream validation was engineered).*

## 2. Endpoints Added
- **`POST /history/upload-preview`**:
  - Requires a `.csv` file. 
  - Iterates every row, validating presence of `project_code` and `report_month`.
  - Enforces cross-referencing against the operational `schedule_monitoring.csv` dataset, throwing row-level errors for unknown project codes.
  - Normalizes string dates into standard `YYYY-MM`.
  - Captures within-file duplicates by caching keys on-the-fly (`f"{code}_{month}"`).
  - Checks bounded values (e.g., Physical progress `0-100`).
  - If **ANY** error is found, it terminates early, blocks staging, and responds with `valid = False` alongside a full list of row-specific errors.
  - If completely valid, generates a unique UUID, dumps a serialized JSON into the isolated staging folder, and returns the UUID alongside a 5-row preview.
- **`POST /history/upload-confirm`**:
  - Accepts the `staging_id` UUID generated by the preview.
  - Looks up the JSON file, loads the array, and strictly pushes it into `historical_store.append_snapshots()`.
  - Enforces atomic isolation: instantly deletes the staging file immediately after read to prevent "double-click" duplication anomalies.

## 3. Validation Behaviors & Test Results
Running `scripts/test_history_ingestion.py` successfully completed all 11 conditions:
1. **Valid first-time import**: Confirmed file is staged and strictly pushes successfully.
2. **Re-importing identical project-month records**: Identified and correctly yielded `updated: 1, inserted: 0`.
3. **Same project across different months**: Inserted successfully independently.
4. **Missing report_month**: Rejected entirely with row-level error.
5. **Missing project_code**: Rejected.
6. **Unknown project code**: Rejected, accurately protecting the ecosystem from rogue codes.
7. **Invalid reporting month format**: Rejected via string parsing exceptions.
8. **Duplicate project-month keys within one file**: Successfully flagged the row and blocked staging.
9. **Invalid numeric values (e.g., > 100% progress)**: Successfully rejected.
10. **Confirmation without valid staged preview**: Immediately returns `HTTP 400` error for expired staging files.
11. **Repeated confirmation (Double-Click)**: The second attempt correctly failed since the staging token self-destructs after a single successful confirmation.

## 4. Remaining Limitations
- **Memory Consumption**: `/history/upload-preview` presently caches the valid rows in memory and then dumps to staging. For very large files (e.g., >500 MB), streaming reads might eventually be required, although currently it safely manages 100,000+ row prototypes easily.
